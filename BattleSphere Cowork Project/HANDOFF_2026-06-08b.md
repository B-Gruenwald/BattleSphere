## Current data model (army-related tables)

### `armies`
Top-level army object, owned by a user (not campaign-scoped).
Columns: `id`, `player_id`, `name`, `faction`, `game_system`, `description`, `is_public`, etc.

### `army_units`
Units belonging to an army.
Columns: `id`, `army_id`, `name`, `unit_type`, `points_cost`, `unit_size`, `sort_order`, etc.

### `campaign_army_records`
Links an army to a campaign (the "deployment").
Columns: `id`, `campaign_id`, `army_id`, `player_id`, `campaign_notes`, `crusade_points`, `supply_limit`, `supply_used`, `battles_played`, `battles_won`, `requisition_points`, `scars_and_upgrades`
Constraint: `UNIQUE(campaign_id, army_id)` — one deployment per army per campaign (already correct).
RLS: public read, owner insert/update/delete.

### `crusade_unit_records`
Per-unit campaign tracking. References `campaign_army_record_id` + `army_unit_id`.
Columns: `experience_points`, `kills`, `crusade_points`, `upgrades`, `scars`

## What to build this session

### Overview
Put army management front and centre. Players should be able to deploy multiple armies to a campaign (across different game systems), manage each army's campaign-specific roster from a dedicated page, and see which campaigns an army is deployed to from their Army Portfolio. The Campaign Dashboard should surface a more prominent "My Forces" entry point.

### 1. DB migrations (write files, then Benjamin runs them in Supabase)

**migration_army_overhaul.sql** — save to "BattleSphere Cowork Project" folder.

Changes needed:

```sql
-- (a) Drop the old UNIQUE constraint that prevented multiple armies per player per campaign
-- The existing constraint is UNIQUE(campaign_id, army_id), which is still correct —
-- one army can only be deployed once to a given campaign. A player can deploy MULTIPLE
-- different armies to the same campaign. No constraint change needed here — confirm this
-- is how it already works before writing any migration.

-- (b) Add faction link: which campaign faction this army fights for
ALTER TABLE campaign_army_records ADD COLUMN IF NOT EXISTS faction_id UUID REFERENCES factions(id) ON DELETE SET NULL;

-- (d) Add army-level Kill Team fields (structured for Kill Team game system)
ALTER TABLE campaign_army_records ADD COLUMN IF NOT EXISTS kt_spec_ops_note TEXT;
ALTER TABLE campaign_army_records ADD COLUMN IF NOT EXISTS kt_equipment_points INT NOT NULL DEFAULT 0;

-- (e) army_battles link: add optional army_id FK to battles table so a battle can be
-- attributed to a specific deployed army
ALTER TABLE battles ADD COLUMN IF NOT EXISTS army_id_p1 UUID REFERENCES armies(id) ON DELETE SET NULL;
ALTER TABLE battles ADD COLUMN IF NOT EXISTS army_id_p2 UUID REFERENCES armies(id) ON DELETE SET NULL;
-- (player 1 and player 2 army selections — optional, nullable)
```

**Logic for which fields to show by game system** (handled in UI, not DB):
- `game_system` on the `armies` table determines which manager view to show.
- **Warhammer 40K / Horus Heresy 30K**: show `crusade_points`, `supply_limit`, `supply_used`, `requisition_points`, `scars_and_upgrades`. Per-unit: XP, kills, crusade_points, upgrades, scars.
- **Kill Team**: show `kt_equipment_points`, `kt_spec_ops_note`, `battles_played`, `battles_won`. Per-unit (operatives): XP / spec ops note only (simpler).
- **All other game systems**: show `campaign_notes` (free-form textarea) + `battles_played` / `battles_won` tally only.

**Current state:** Deploying is buried in the user's "My Profile" page inside a campaign. It's unclear and limited.

**New flow:**

**B. From Army Portfolio page (`app/armies/[id]/page.js` or edit page)**

- API route: `POST /api/campaign-armies` — body `{ campaign_id, army_id }`. Checks player is a member of the campaign. Returns the new record.

### 3. "My Forces" page — `/c/[slug]/forces`

New page replacing the old "My Profile" campaign army view. Server component wrapper + client components for editing.

**Layout:**
- Page title: "My Forces — [Campaign Name]"
- One card per deployed army, showing:
  - Army name
  - Faction badge (which campaign faction they fight for — editable via dropdown of campaign factions)
  - Game system badge
  - Army thumbnail / photo if available
  - Link to **"Manage Roster →"** which goes to `/c/[slug]/forces/[armyId]`
  - Battles played / won in this campaign (pulled from `campaign_army_records`)
- **"+ Deploy Another Army"** button at the bottom of the list — opens the deploy modal (same as from Army Portfolio).
- If no armies deployed yet: empty state "No forces deployed — deploy your first army to join the campaign."

**API routes needed:**
- `GET /api/campaign-armies?campaign_id=&player_id=` — returns all `campaign_army_records` for this player in this campaign, joined with army name/faction/game_system.
- `PATCH /api/campaign-armies/[id]` — update `campaign_nickname`, `faction_id`, and any roster stats fields.
- `DELETE /api/campaign-armies/[id]` — un-deploy army from campaign.

### 4. Army Roster Manager — `/c/[slug]/forces/[armyId]`

Dedicated page for managing one army's campaign-specific data. This replaces the old crusade stats embedded in the player profile.

**Layout:**
- Header: Army name + faction + game system badge + link back to "My Forces"
- **Campaign Stats section** — shown/hidden fields based on `game_system` (see logic above):
  - 40K: Supply Limit / Supply Used / Crusade Points / Requisition Points / Scars & Upgrades

  - Kill Team: Equipment Points / Spec Ops Note
  - Other: Campaign Notes (textarea) only
  - All: Battles Played / Battles Won (always shown, auto-updated when battles are linked)
- **Unit Roster section** — list of units from `army_units`, each with their `crusade_unit_records` for this campaign inline (XP, kills, upgrades, scars for 40K; XP only for KT; nothing extra for other systems). Units not yet enlisted in the campaign get an "Enlist" button that creates a `crusade_unit_records` row.
- **Battle Record section** — list of battles in this campaign where `army_id_p1` or `army_id_p2` matches this army's id. Each row: date, opponent, result, territory. Links to battle detail.
